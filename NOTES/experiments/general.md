## 🔄 The Active Learning Loop: A Conceptual Overview

This experiment is designed around a central active learning loop. The goal of this loop is to iteratively refine a **version space**—a geometric representation of all possible models consistent with the user's preferences—by asking a series of optimal questions.

The process unfolds as follows:

1.  **Initialization**:

      * The experiment starts with a dataset of items and an oracle (representing the user's true preferences).
      * A version space is initialized as a simple, high-dimensional polytope (e.g., a hypercube) that contains all possible linear models.
      * Spatial data structures (**kd-tree** and **ball-tree**) are built on the dataset items to accelerate the search for queries. These trees are logged once.

2.  **The Loop (Repeated `m` times)**:

      * **Find Center**: The geometric center of the current version space is calculated. This "center model" is our best guess for the user's preferences at this iteration.
      * **Search for Query**: A branch-and-bound search is performed over the dataset, using the trees, to find the most informative query (e.g., a pair of items) to ask the oracle. This search process is the most computationally intensive part and is logged in detail for each iteration.
      * **Query Oracle**: The optimal query is presented to the oracle, which provides a response (e.g., "I prefer item A over item B").
      * **Update Version Space**: The oracle's response is translated into a new linear constraint (a hyperplane). This hyperplane is used to slice the version space, reducing its volume and thus refining our knowledge of the true model. The new constraint is added to our list.

3.  **Termination**:

      * After the budget of `m` queries is exhausted, the loop terminates.
      * The final, refined version space, defined by the complete, ordered set of `m` constraints, is saved.

This entire process, from initialization to the final slice, is meticulously logged into a series of raw data files, allowing for complete and flexible post-experiment analysis.

## 🌍 Top-Level Files: Global Experiment Data

These files reside at the root of the experiment directory and store data that applies to the entire run.

### 1\. `config.json`

This is the **master record** of the experiment's setup. It's a human-readable JSON file that contains all parameters necessary to reproduce the run.

  * **Purpose**: To provide a complete and exact specification of the experimental conditions.
  * **Format**: JSON
  * **Contents**:
    ```json
    {
      "experiment_uid": "a1b2c3d4",
      "dataset_name": "TOY",
      "oracle_name": "LinearOracle",
      "center_name": "AnalyticCenter",
      "dataset_path": "/path/to/data/toy_dataset.npy",
      "dataset_hash": "sha256:...",
      "random_seed": 1729,
      "active_learning_budget": 100,
      "algorithm_parameters": {
        "leaf_size": 25,
        "search_strategies": [
          "lower_bound",
          "upper_bound_pruning"
        ],
        "tree_build_methods": {
          "kdtree": ["default"],
          "balltree": [
            "axis_median",
            "bottom_up",
            "disjoint_greedy",
            "middle_out",
            "pca_ballstar",
            "two_pivot"
          ]
        }
      }
    }
    ```

### 2\. `final_version_space.h5`

This file captures the **final geometric state** of the version space polytope after the last active learning iteration.

  * **Purpose**: To store the complete mathematical definition of the final learned model space.
  * **Format**: HDF5
  * **Internal Structure**:
      * **/A**: A numerical matrix of shape `(m, d)`, where `m` is the number of queries made and `d` is the dimensionality. Each row is a hyperplane's normal vector.
      * **/b**: A numerical vector of shape `(m, 1)`. Each entry is the offset for the corresponding hyperplane.
      * **Constraint Order**: The rows in `A` and `b` are **ordered chronologically**. The `i`-th row corresponds to the constraint generated by the query in iteration `i`.

### 3\. `query_vectors.h5`

A centralized binary file containing every query vector generated during the experiment.

  * **Purpose**: To efficiently store all numerical query vectors, avoiding text-based formats.
  * **Format**: HDF5
  * **Internal Structure**:
      * A series of datasets, one for each iteration. The dataset for iteration `i` is named `/query_i` and contains the `d`-dimensional query vector.

### 4\. `iterations.csv`

A lightweight, high-level summary of the active learning process. It logs the events of each iteration without storing heavy data directly.

  * **Purpose**: To provide a simple, human-readable timeline of the query-response cycles.
  * **Format**: CSV
  * **Columns**:

| Column          | Description                                                              | Data Type      | Example                         |
| :-------------- | :----------------------------------------------------------------------- | :------------- | :------------------------------ |
| `iteration_id`  | Zero-indexed integer for the iteration number.                           | Integer        | `42`                            |
| `query_path`    | The path inside `query_vectors.h5` to this iteration's query vector.     | String         | `"/query_42"`                   |
| `oracle_response`| The raw response received from the oracle.                               | String/Integer | `"item_A_preferred"` or `1`     |
| `timestamp_start`| Wall-clock time when the iteration began (ISO 8601).                     | String         | `"2025-09-28T10:11:15.123Z"`    |
| `timestamp_end` | Wall-clock time when the iteration ended (ISO 8601).                     | String         | `"2025-09-28T10:11:17.456Z"`    |

### 5\. `tree.h5`

This file contains the raw structural data for the **kd-tree and ball-tree** built at the beginning of the experiment. It allows for a perfect, byte-for-byte reconstruction of the trees used during the search.

  * **Purpose**: To store the complete topology and bounding information of the spatial index trees.
  * **Format**: HDF5
  * **Internal Structure**:
      * **/kdtree/nodes**: A table where each row defines a single node in the kd-tree.
      * **/balltree/nodes**: A table where each row defines a single node in the ball-tree.
  * **Node Table Columns**:

| Column        | Description                                                                               | Data Type |
| :------------ | :---------------------------------------------------------------------------------------- | :-------- |
| `node_id`     | A unique identifier for the node.                                                         | Integer   |
| `parent_id`   | The `node_id` of the parent. The root's parent is -1.                                     | Integer   |
| `is_leaf`     | A boolean flag indicating if this is a leaf node.                                         | Boolean   |
| `child_left`  | `node_id` of the left child (or -1 if leaf).                                              | Integer   |
| `child_right` | `node_id` of the right child (or -1 if leaf).                                             | Integer   |
| `split_dim`   | **(kd-tree only)** The index of the feature/dimension used for the split at this node.      | Integer   |
| `split_val`   | **(kd-tree only)** The threshold value on the `split_dim` that separates children.         | Float     |
| `ball_center` | **(ball-tree only)** The `d`-dimensional vector for the center of the bounding ball.      | Float Array|
| `ball_radius` | **(ball-tree only)** The radius of the bounding ball.                                     | Float     |
| `point_indices`| A list of indices of the raw data points contained within this node's region.           | Integer Array|

## 🔬 Iteration Subdirectories: The Details

For each active learning cycle, a subdirectory is created to hold the fine-grained raw data generated during that step.

**Directory Name**: `iteration_042/`

### 1\. `search_trace.h5`

This is the **detective's notebook**: a granular, moment-by-moment log of every action taken by the branch-and-bound algorithm while it searched for the optimal query in this single iteration.

  * **Purpose**: To capture the complete, unsummarized event history of the search process, enabling deep post-analysis of the algorithm's behavior.
  * **Format**: HDF5, containing a single table-like dataset.
  * **Internal Structure (`/events` dataset)**:

| Column        | In-Depth Explanation                                                                                                 | Data Type      | Example                |
| :------------ | :------------------------------------------------------------------------------------------------------------------- | :------------- | :--------------------- |
| `event_type`  | The action taken: **`CREATED`** (node identified), **`EXPANDED`** (node explored), or **`PRUNED`** (node discarded). | String         | `"PRUNED"`             |
| `node_id`     | A unique identifier for the search node (a specific region of the search space).                                     | Integer        | `1337`                 |
| `parent_id`   | The `node_id` of the node that generated this one. Used to reconstruct the search tree.                                  | Integer        | `1201`                 |
| `timestamp`   | High-precision Unix timestamp of when the event occurred.                                                            | Float          | `1664352677.123456`    |
| `lower_bound` | An optimistic guarantee: the solution in this node's region is worth *at least* this much.                             | Float          | `0.85`                 |
| `upper_bound` | A pessimistic guarantee: the solution in this node's region is worth *no more than* this much.                          | Float          | `0.95`                 |

### 2\. `center_model.npy`

A simple binary file containing the single most important piece of information about the model's state at the end of this iteration.

  * **Purpose**: To store the representative model vector for this iteration, from which performance will be calculated during analysis.
  * **Format**: NumPy `.npy`
  * **Contents**:
      * A single `d`-dimensional NumPy array. This vector represents the **center of the version space** *after* the current iteration's query and response have been incorporated.
